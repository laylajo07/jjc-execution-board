# 평가·비교 — 접근법 A(웹페이지) vs B(직접) · 제출 추천

> 주제: 형식이 제각각인 회의록 → 부서·구성원별 할일·문서·의사결정·진행순서 + 부서별 공유
> 공통 테스트 입력: `회의록/샘플01_불규칙메모`
> 두 접근법 모두 **동일한 코크핏 웹앱 "조정치"** 형태로 제작해, 차이는 **시스템 프롬프트(=두뇌)**에서 발생.

---

## 1. 한눈에 보는 결론

- **산출물 품질(구조화 정확도·견고함)·제약 적합성** → **접근법 B(클로드 직접 설계)** 가 우위.
- **제작 속도·발표/테스트 부가자료** → **접근법 A(사내 웹페이지)** 가 우위(자동 생성).
- ✅ **제출 추천**: **B를 본체(프롬프트+앱)로 제출하고, A가 만들어준 발표 스피치·테스트 시나리오를 그대로 얹는다.**
  둘 다 같은 앱·러너를 쓰므로 결합이 자연스럽다. 굳이 폴더 하나만 낸다면 → **`B_직접`**.

## 2. 점수표 (5점 만점)

| 기준 | A · 웹페이지 | B · 직접 | 근거 |
|---|:---:|:---:|---|
| 커버리지(할일·문서·의사결정·순서) | 4.5 | 5.0 | 둘 다 4대 항목 커버. B는 Top3·요약·부서표준화까지 |
| 정확도(사실 왜곡·담당/기한) | 4.0 | 4.5 | B는 상대날짜를 절대날짜로 환산(7/15·7/18·8/15) |
| 견고함(불확실성·형식 제각각) | 3.5 | 5.0 | B는 확정/추정/확인필요 3단계+근거, 가정·갭 분리, 자기검증 |
| 사용성·재현성(제약 적합) | 3.0 | 5.0 | A 기본 개발가이드는 **API키 Python CLI**(제약 불일치). B는 무API 코크핏 설계 |
| 제작 속도/노력 | 5.0 | 3.5 | A는 클릭 몇 번(약 10분). B는 프롬프트 직접 설계 |
| 부가 산출물(발표·테스트) | 5.0 | 3.0 | A는 1분 스피치·슬라이드·테스트 3종 자동 생성 |
| **총점(단순합)** | **25.0** | **26.0** | 품질·제약에서 B가 역전 |

## 3. 시스템 프롬프트 비교

| 항목 | A(웹 생성) | B(직접 설계) |
|---|---|---|
| 부서 표준화 | 본부 나열만 | 원문→표준본부 **매핑 규칙표**, 사람↔부서 [미상] 처리 |
| 불확실성 | '확인 필요' 단일 | **확정/추정/확인필요 3단계 + 근거(basis)**, assumptions·gaps 분리 |
| 진행 순서 | 화살표(부서별 분산) | **위상정렬 sequence + blocked_by/blocks + 병목·순환 경고** |
| 실행 즉시성 | 없음 | **한 줄 요약 + 지금 할 일 Top 3** |
| 날짜 | 규칙 없음(상대표현 유지) | **상대→절대 환산 규칙**(회의일 불명 시 확인필요) |
| 공유 메시지 | 메신저/이메일 | 동일 + **이메일 제목 분리, 확인필요는 질문형 톤** |
| 견고성 | 언급 없음 | **빈 입력/무의미 입력 처리 + 자기검증 STEP** |

## 4. 같은 회의록(샘플01)에 대한 실제 출력 차이

| 관찰 포인트 | A 출력 | B 출력 |
|---|---|---|
| 핵심 병목 식별 | 표시 없음 | **⚠️ "v2 재학습"이 3개 후행을 막는 병목**으로 명시 |
| 이사회 자료 일정 모순 | gaps에 1줄 언급 | **순서 7단계에서 "선행 미완인데 기한 먼저 → 순서 충돌"** 로 경고 |
| 상대 날짜 | "다음주 화요일" 그대로 | **2026-07-15(화)** 등 절대날짜 환산(가정에 근거 명시) |
| 요약/우선순위 | 없음 | 한 줄 요약 + Top 3 |
| 담당/기한 근거 | 없음 | 각 항목 basis(근거) 표기 |
| 부서 커버리지 | 6개 부서 | 6개 부서(동일) |

두 결과 모두 **담당·기한이 없는 항목을 지어내지 않고 '확인 필요'로 처리**하는 핵심 요건은 충족.
B는 여기에 더해 **"무엇이 무엇을 막는지"와 "언제까지"**를 실행 가능한 수준으로 끌어올림.

## 5. "앱" 관점의 결정적 차이 (사용자 제약: API 키 없음·로컬 로그인)

- **A의 기본 개발 가이드**는 ⑤단계에서 *Anthropic Python SDK로 API를 호출하는 CLI*를 만들라고 안내 → **API 키 필요**. 사용자의 "로컬 로그인만 사용" 제약과 **불일치**.
- **B(및 본 프로젝트)** 는 이를 **코크핏 웹앱 + 공용 러너(`claude -p`)** 로 해결 → **API 키 0**, 로컬 로그인 그대로.
- ※ 공정성을 위해 A의 앱도 **A의 프롬프트를 그대로 넣어 같은 코크핏 형태**로 제작함(그래서 A도 실사용 가능). 즉 위 불일치는 "A를 가이드대로 따랐을 때"의 한계이며, 본 제출물에서는 보완됨.

## 6. 검증 로그

- A/B 앱 모두 로컬 서버로 띄워 **실제 렌더링 확인**(부서 6, 진행순서 9·병목 4, 공유메시지 12, 상태배지 22).
- **자동 모드 end-to-end 실제 실행**: TS(pnpm) 러너 + Python 러너 모두 기동 확인, `claude -p`(로컬 로그인·API 키 0)로 샘플01을 실제 처리해 `결과/`에 저장·화면 렌더링.
- 렌더러는 A·B 두 JSON 스키마를 모두 정규화(normalize)해 표시 → 동일 앱으로 공정 비교.
- UI 헤더에 **모델 선택 드롭다운**(러너 기본/Haiku/Sonnet/Opus) 추가 → 요청마다 `--model` 전달(모델명 화이트리스트 검증).
- **A·B 동시 비교**: A=8788, B=8787 두 러너를 동시에 띄워 각자 앱으로 정상 동작 확인(`실행방법.md`).
- **결과 스트리밍(SSE)**: 러너가 `claude -p` 출력을 실시간 전달, 웹앱이 생성 과정을 표시 후 보드 렌더링.
- **모드 토글**: 헤더 표시등 클릭으로 자동↔복붙 수동 전환 확인. 직접 붙여넣기 입력칸 확대(300px).
- 스크린샷(새 디자인): `문서/스크린샷/실행보드_라이트.png`, `문서/스크린샷/실행보드_다크.png`.

### ⏱ 운영 관찰 — `claude -p` 지연
- `claude -p`는 요청마다 Claude Code 세션을 새로 부팅 → **모델과 무관하게 1~3분** 소요(세션 부팅이 대부분).
- 시연/반복 사용에는 **복붙 모드**(이미 로그인된 창에 붙여넣기)가 체감상 더 빠름. 자동 모드는 "버튼 한 번" 편의가 강점.

## 7. 최종 제출안

1. **본체**: `B_직접/` (시스템 프롬프트 `시스템프롬프트.md` + 앱 `앱/index.html` + 실행결과).
2. **발표**: `A_웹페이지/발표자료.md` (1분 스피치·슬라이드 불릿) 재사용.
3. **테스트**: `A_웹페이지/진행기록.md` 의 테스트 시나리오 3종(정상/애매/예외) → `회의록/샘플02~04` 로 시연.
4. **실행**: `러너`(TS/pnpm 또는 Python)로 자동 모드 시연, 또는 앱 더블클릭 복붙 모드.

> 요약: **"클로드에게 직접"이 결과물 품질에서 앞섰지만, 웹페이지는 온보딩·발표자료에서 강했다.
> 둘을 합쳐 B 엔진 + A 발표자료로 제출하는 것이 최선.**
