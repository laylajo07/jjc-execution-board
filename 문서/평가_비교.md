# 평가·비교 — 접근법 A(웹페이지) vs B(직접) · 제출 추천

> 주제: 형식이 제각각인 회의록 → 부서·구성원별 할일·문서·의사결정·진행순서 + 부서별 공유

> 두 접근법 모두 **동일한 코크핏 웹앱 "조정치"** 형태로 제작해, 차이는 **시스템 프롬프트(=두뇌)**에서 발생.

## 1. 한눈에 보는 결론

- **산출물 품질(구조화 정확도·부서 표준화)·제약 적합성** → **접근법 B(클로드 직접 설계)** 가 우위.
- **제작 속도·발표/테스트 부가자료** → **접근법 A(사내 웹페이지)** 가 우위(자동 생성).
- ⚠️ **창작(지어내기) 억제력은 A·B 동급**. 함정 케이스(샘플03 애매·04 예외)에서 **양쪽 모두 담당자·기한 창작 0건**.
  당초 B의 우위로 봤던 '견고함'은 n=1(샘플01) 근거였고, n=4에서는 차이가 거의 없었다.
- ✅ **제출 추천(유지)**: **B를 본체(프롬프트+앱)로 제출하고, A가 만들어준 발표 스피치·테스트 시나리오를 그대로 얹는다.**
  둘 다 같은 앱·러너를 쓰므로 결합이 자연스럽다. 굳이 폴더 하나만 낸다면 → **`B_직접`**.
  n=4 검증 결과 A의 강점이 **정확히 부가자료 영역**에 몰려 있음이 수치로 확인되어, 이 결합안의 근거가 오히려 강해졌다(2절).

### 2-1. 단순합이 오해를 부르는 이유 — 축을 나눠 보면

단순합은 "만들기 편했나"(제작 속도·부가자료)를 "제출물이 좋은가"(품질·제약)와 **같은 무게로 더한다.**
제출 판단에 실제로 쓰이는 축만 떼어 보면 결론은 명확하다.

| 축 묶음 | A | B | 판정 |
|---|:---:|:---:|---|
| **산출물 품질·제약** (커버리지+정확도+견고함+사용성) | 16.0 | **19.5** | **B 확연 우위 (+3.5)** |
| **제작 편의** (속도+부가산출물) | **10.0** | 6.5 | A 우위 (+3.5) |
| 단순합 | 26.0 | 26.0 | 동점 |

→ **A의 우위는 전부 "제작 편의"에서 나온다.** 즉 A는 *결과물*이 아니라 *만드는 과정과 곁다리 자료*가 강했다.
이는 7절의 결합안(**B 엔진 + A 발표자료**)이 두 접근법의 강점을 정확히 갈라 취하고 있음을 뒷받침한다.

## 3. 시스템 프롬프트 비교

| 항목 | A(웹 생성) | B(직접 설계) |

| 불확실성 | 확정/추정/확인필요 3단계(동일) · gaps만 | 3단계 + **근거(basis)**, **assumptions·gaps 분리** |
| 진행 순서 | 화살표(부서별 분산) | **위상정렬 sequence + blocked_by/blocks + 병목·순환 경고** |

B는 여기에 더해 **"무엇이 무엇을 막는지"와 "언제까지"**를 실행 가능한 수준으로 끌어올림.

### 4-1. 샘플02~04 검증 (2026-07-16 · 각 건 독립 세션 실행 · 상세는 [`검증_샘플02-04.md`](./검증_샘플02-04.md))

판정 기준은 `A_웹페이지/진행기록.md` 에 A 웹페이지가 미리 적어둔 **기대출력**.

| 샘플 | 핵심 판정 항목 | A | B |
|---|---|:---:|:---:|
| 02 정상 | 담당·기한·확정 판정, 의사결정, 선후행 | ✅ 전부 | ✅ 전부 |
| 03 애매 | 부서 섹션(영업·법무) | △ `영업팀`·`법무` **원문 그대로** | ✅ `고객솔루션본부(영업)`·`법무실` |
| 03 애매 | 담당·기한 전량 확인필요, NDA 담당 미배정 | ✅ | ✅ |
| 04 예외 | 할 일 정확히 2건만 추출, 창작 없음 | ✅ | ✅ |
| 04 예외 | 부서에 `[알 수 없음]` 병기 | ❌ | ❌ |
| 전체 | JSON 유효성 | 3/3 | 3/3 |

**관찰 1 · 창작 억제는 동급.** 함정 2건에서 양쪽 다 담당자·기한 창작 0건. 둘 다 "경영지원팀장"을 KPI 취합 담당자로 넣지 않고 **지시자**로만 처리했다. → 견고함 점수 재조정의 근거(2절).

**관찰 2 · 04의 ❌는 에이전트 결함이 아니라 기대출력의 오류.** A·B 모두 같은 근거로 병기를 생략했다 — "경영지원팀장"·"ICT"는 매핑이 **명확**하고, 이 회의록에서 불확실한 건 부서가 아니라 **사람**(양쪽 다 참석자 전원 `[미상]` 처리). 기대출력을 만든 것이 A 웹페이지인데 정작 A 자신도 그렇게 출력하지 않았다. → **기대출력 쪽을 정정해야 한다.**

**관찰 3 · 샘플03 NDA 귀속에서는 A가 더 보수적 — B의 감점 요인.**
회의록 원문은 "NDA 초안 **누가 쓸지 얘기하다 말았고**" 뿐이라 작성 주체가 미확정이다.
- **A**: `[알 수 없음]` 부서를 별도 생성해 NDA를 격리 → 어느 부서에도 귀속 안 함.
- **B**: NDA를 **`법무실` 밑에 배치**. `assumptions`에 "귀속 미확정"을 적었으나, 보드에서는 법무실 산출물로 렌더링된다.

B의 [핵심 원칙] 1번("지어내지 않는다")에 비추면 B가 자기 원칙을 살짝 어긴 쪽이다. 보드를 보는 사람은 assumptions까지 읽지 않고 "NDA는 법무 일"로 받아들인다.
→ **개선안**: B 프롬프트에 "귀속이 미확정인 항목은 `[미상]` 부서로 분리한다" 규칙 추가 검토.

**관찰 4 · A의 구조적 결함 2건 (샘플02에서 노출).**
- `documents` 에 `"확인 필요"` **플레이스홀더가 문서 엔트리로 삽입** → 렌더링 시 빈 문서 카드 발생.
- 동일 의존 간선이 **2회 중복**. A 스키마가 `dependencies` 를 **부서별 배열**로 두어 본부 간 관계를 양쪽에 복제할 수밖에 없는 **구조적 한계**(B는 최상위 `sequence` 하나로 해결).

## 5. "앱" 관점의 결정적 차이 (사용자 제약: API 키 없음·로컬 로그인)

- **A의 기본 개발 가이드**는 ⑤단계에서 *Anthropic Python SDK로 API를 호출하는 CLI*를 만들라고 안내 → **API 키 필요**. 사용자의 "로컬 로그인만 사용" 제약과 **불일치**.
- **B(및 본 프로젝트)** 는 이를 **코크핏 웹앱 + 공용 러너(`claude -p`)** 로 해결 → **API 키 0**, 로컬 로그인 그대로.
- ※ 공정성을 위해 A의 앱도 **A의 프롬프트를 그대로 넣어 같은 코크핏 형태**로 제작함(그래서 A도 실사용 가능). 즉 위 불일치는 "A를 가이드대로 따랐을 때"의 한계이며, 본 제출물에서는 보완됨.

### ⏱ 운영 관찰 — `claude -p` 지연
- `claude -p` 소요 시간은 세션 부팅이 아니라 **출력 길이에 비례**합니다(짧은 프롬프트는 5초, 실행보드 전체 생성은 수 분). `--output-format stream-json`으로 진행 상황이 실시간 표시되도록 수정함(2026-07-16).
- 시연/반복 사용에는 **복붙 모드**(이미 로그인된 창에 붙여넣기)가 체감상 더 빠름. 자동 모드는 "버튼 한 번" 편의가 강점.
