# 회의록 → 실행계획 Agent · 설계문서

- **작성일**: 2026-07-14
- **작성/의뢰**: 테크핀레이팅스 PM (사내 AI 해커톤 참가작)
- **상태**: 확정 (사용자 승인 완료)

## 1. 목표 (Agent 주제)

형식이 **일정하지 않게 작성된 회의록 텍스트**를 입력하면, 회의에 참여한
**부서·구성원별로**:

1. **해야 할 업무 (Action Items)** — 누가, 무엇을, 언제까지
2. **작성해야 할 문서 (Deliverables)** — 어떤 문서를, 누가
3. **의사결정이 필요한 부분 (Open Decisions)** — 무엇을, 누가 결정, 언제
4. **진행 순서 (Sequence / Dependencies)** — 무엇 먼저, 무엇이 무엇을 막는지

를 도출하고, **부서별 공유 메시지/이메일**까지 만들어 공유하게 한다.

## 2. 실험 방식 (해커톤 제출 전략)

동일한 산출물을 **두 접근법으로 병렬 제작**하고 더 나은 것을 제출한다.

| | 접근법 A | 접근법 B |
|---|---|---|
| 방식 | 사내 AI팀 웹페이지(techfin-agent-builder)에서 상황 입력 → 생성된 프롬프트를 Claude에 사용 | Claude에게 직접 요청 |
| 폴더 | `A_웹페이지/` | `B_직접/` |

두 산출물은 **같은 형태**(시스템 프롬프트 + 코크핏 웹앱)로 만들고, 같은 샘플
회의록으로 실행해 **평가_비교.md**에서 비교 후 제출본을 추천한다.

## 3. 산출물 형태 — "회의록 코크핏" 웹앱 + Claude Code 엔진

API 키를 쓰지 않는다. **로컬에 로그인된 Claude(Claude Code)** 가 두뇌 역할을 한다.

```
① 코크핏 웹앱 (단일 HTML, 더블클릭 실행)
   · "프로젝트 폴더 연결" (File System Access API, 권한 1회)
   · 회의록/ 목록 표시, 드래그드롭으로 추가
   · [분석] 버튼 → 요청 기록 + "Claude Code에서 실행하세요" 안내
        │
        ▼
② Claude Code (사용자 로그인) = 엔진
   · 폴더의 스킬/지시 .md (= 시스템 프롬프트) 를 읽고 처리
   · 회의록/ 의 회의록 → 구조화
   · 결과/ 에 산출물(JSON + MD) 저장
        │
        ▼
③ 웹앱이 결과/ 폴더를 감시(폴링) → 렌더링
   부서별 할일 보드 · 진행순서 타임라인 · 의사결정 체크리스트 · 부서별 공유메시지
```

- 웹앱은 Claude를 **강제 실행하지 않고 안내만** 한다(브라우저 보안).
- 폴더 접근은 Chrome/Edge의 File System Access API. `file://`에서 막히면 로컬 정적서버 폴백.
- `.bat` 런처는 만들지 않는다.

## 4. 폴더 구조

```
새 폴더/
├── README.md              ← 시작점
├── 지시사항.md
├── 회의록/                 ← 회의록 넣고 빼는 입력 폴더
│   ├── 샘플01~04.md
│   └── README.md          ← 회의록 추가/교체 방법
├── A_웹페이지/             ← 접근법 A
│   ├── 시스템프롬프트.md · 진행기록.md · 발표자료.md · 실행결과_샘플01.md
│   └── 앱/  (index.html, AGENT.md, 결과/)
├── B_직접/                 ← 접근법 B
│   ├── 시스템프롬프트.md · 실행결과_샘플01.md
│   └── 앱/  (index.html, AGENT.md, 결과/)
├── 러너/                   (py/, ts/, README.md)
└── 문서/                   (평가_비교.md, 실행방법.md, 설계.md, 스크린샷/)
```

## 5. 에이전트 출력 스키마 (JSON, 두 접근법 공통 목표)

```jsonc
{
  "meeting": { "title": "", "date": "", "attendees": [ {"name":"","dept":"","role":""} ] },
  "by_department": [
    {
      "dept": "",
      "action_items": [ {"what":"","owner":"","due":"","confidence":"확정|추정"} ],
      "documents": [ {"doc":"","owner":"","due":""} ],
      "decisions_needed": [ {"topic":"","decider":"","by":"","note":""} ]
    }
  ],
  "sequence": [ {"step":1,"task":"","blocks":[],"blocked_by":[]} ],
  "share_messages": [ {"dept":"","channel":"메신저|이메일","text":""} ],
  "assumptions": [ "" ],   // 회의록에 없어서 추정한 부분 (투명하게 표기)
  "gaps": [ "" ]           // 담당자/기한 등 누락돼 확인 필요한 항목
}
```

핵심 원칙: **불확실한 것은 지어내지 말고 `assumptions`/`gaps`로 분리**한다.

## 6. 비교 평가 기준 (평가_비교.md)

1. **커버리지** — 4대 항목(할일/문서/의사결정/순서)을 부서별로 빠짐없이?
2. **정확도** — 샘플 회의록의 사실을 왜곡/누락 없이? 담당·기한 정확?
3. **견고함** — 형식 제각각/누락 정보에 대한 처리(추정·갭 표기)
4. **사용성/재현성** — 비개발자가 쓰기 쉬운가, 결과가 바로 공유 가능한가
5. **제작 노력/속도**

## 7. 범위 밖 (YAGNI)

- 실시간 STT(음성→텍스트), 캘린더/메신저 자동 발송 연동, 다국어 — 이번 범위 아님.
- API 키 기반 자동 호출 — 사용 안 함.
