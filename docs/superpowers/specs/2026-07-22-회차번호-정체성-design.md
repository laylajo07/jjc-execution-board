# 회차 번호를 "정체성"으로 승격 (지시사항 15–20)

- 작성일: 2026-07-22
- 대상: `B_직접/앱/` (제출본) 및 `A_웹페이지/앱/` — 공용 순수 모듈은 A·B 바이트 동일 유지
- 관련 지시: 지시사항.md 15–20
- 선행 설계: `2026-07-21-프로젝트-히스토리-design.md`(회차 누적·diff), `2026-07-21-보드-업데이트일시-design.md`

## 1. 배경 / 문제

현재 회차(round)는 **처리 순서대로 배열에 append**되고, 회차의 정체성은 곧 처리 위치다
(`round = {id:'r_N', ts, title, raw}`). diff 기준(baseline)은 "배열 직전 회차"(`rounds[idx-1]`),
히스토리 목록도 처리 순서로 렌더한다.

지시 15–20은 이 모델을 뒤집는다: **회차 번호(roundNo)는 사용자가 지정하는 고유 식별자이며,
분석을 몇 번째로 실행했는가(처리 순서)와 절대 동일시하지 않는다.** diff 기준·정렬·재계산이
모두 처리 순서가 아니라 회차 번호로 결정되어야 한다.

## 2. 목표 / 비목표

**목표**
- 분석 전 (1) 회의록 파일 · (2) 프로젝트 · (3) **회차 번호(숫자)** 를 명시적으로 입력 (15)
- 회차 번호 = 사용자 지정 고유 식별자, 처리 순서와 분리 (16)
- 저장 필드: 프로젝트 ID · 회차 번호 · 회의록 ID · 분석 결과 · 처리 시각, 회차 번호로 조회·정렬 (17)
- diff 기준 = 같은 프로젝트의 이미 분석된 회차 중 roundNo가 현재보다 작은 것 중 **최대** (18)
- 재분석 시 그 회차를 기준으로 삼던 후속 회차가 있으면 확인 후 재계산, 거부 시 "기준 오래됨" 표시 (19)
- 히스토리 목록은 roundNo 오름차순 + 처리 일시 병기 (20)

**비목표 (YAGNI)**
- 회차별 diff 요약을 별도 저장하지 않는다(diff/digest는 지금처럼 렌더 시 라이브 계산).
- 다단계 연쇄는 없다 — 재분석/삽입은 **직접 후속 회차 하나**의 기준만 바꾼다(§6 근거). 코드는 집합으로
  일반 처리하되 실제로는 0–1건.
- 드래그 재정렬·회차 번호 이외 라벨·프로젝트 간 기준 참조는 다루지 않는다.

## 3. 데이터 모델 (`project-store.js`, A·B 바이트 동일)

회차 레코드 확장:

```
round = {
  id,            // 내부 안정 키 'r_N' (currentRoundId 배선용, 유지)
  roundNo,       // ✚ 양의 정수, 사용자 지정 (16·17)
  noteId,        // ✚ 회의록 식별자(파일명). 복붙 입력 시 '' (17)
  ts,            // 처리 시각 (기존)
  title, raw,    // 기존
  baselineNo,    // ✚ 이 회차 diff의 기준 회차 roundNo (없으면 null)
  baselineStamp  // ✚ 그 기준 회차의 ts를 마지막으로 정합화한 값 (없으면 '')
}
```

`baselineNo`/`baselineStamp`는 **정합화 마커**다. diff 자체는 저장하지 않고, 이 두 값이
"현재 올바른 기준(roundNo, ts)"과 어긋나면 그 회차를 stale로 판정한다(§6).

### 함수 변경

- **`sanitizeProject`** — roundNo 마이그레이션을 흡수(멱등). 각 회차의 roundNo를 양의 정수로
  강제하고 프로젝트 내 유일성을 보장한다. 2-pass:
  1. 배열 순서대로, 유효한 양의 정수이고 아직 안 쓰인 roundNo는 그대로 채택(used에 등록).
  2. 남은(누락·중복·비정수) 회차에 배열 순서대로 **사용되지 않은 최소 양의 정수**를 배정.
  → 기존 데이터(roundNo 전무)는 1,2,3…으로, 즉 기존 처리 순서대로 이관된다. noteId 없으면 ''.
  baselineNo/baselineStamp 없으면 각각 null/''.
- **`addRound(state, projectId, round)` → `state`** (반환 shape 유지 — 기존 테스트 다수가
  `state = addRound(...)`) — **roundNo 기준 upsert**. `round.roundNo`가 주어지고 같은 프로젝트에
  이미 있으면 그 회차를 **교체**(같은 `id` 유지, ts는 새 처리시각, title/raw/noteId 갱신,
  baselineNo/baselineStamp는 null/''로 초기화 → 호출자가 재설정) = 재분석. `round.roundNo`가 없으면
  `max roundNo + 1`로 **append**(기존 `r_1..r_N` 순번·20캡 동작 그대로 재현). 저장된 회차 id는
  `getRoundByNo`로 호출자가 조회한다.
- **`getRoundByNo(project, roundNo)`** (순수) — roundNo로 회차 조회(없으면 null). upsert 후
  `currentRoundId` 배선용.
- **`findBaseline(project, roundNo)`** (순수) — 그 프로젝트에서 roundNo가 인자보다 작은 회차 중
  roundNo 최대인 회차를 반환(없으면 null). 지시 18의 유일한 판정 지점.
- **`roundsUsingBaseline(project, roundNo)`** (순수) — baselineNo === roundNo인 회차 목록
  (재분석 영향 회차 후보).
- **`setRoundBaseline(state, projectId, roundId, baselineNo, baselineStamp)`** (불변) —
  정합화 마커만 갱신. "다시 계산" 수락 시 사용.
- **`roundsSortedByNo(project)`** (순수) — roundNo 오름차순 사본(20의 렌더 정렬).

`board-diff.js`는 **변경 없음**: `diffBoards(prev, cur)`는 prev를 어떻게 고르는지에 무관하다.
"기준을 무엇으로 고르는가"는 아래 배선(index.html)에서만 바뀐다 → board-diff.js 바이트 동일 자동 유지.

## 4. 입력 단계 UI (`index.html`, A·B 각각)

프로젝트 선택 아래, "직접 붙여넣기" 위에 회차 번호 입력 추가:

```
[ 회차 번호 (숫자) ]  ← 파일명에서 추론한 기본값, 사용자가 수정 가능
```

- 자동 모드: 회의록 파일 선택 시 `inferRoundNo(filename)`로 기본값 채움.
- 복붙 모드: 파일 드롭다운이 없으므로 회차 번호칸은 **항상 노출**, 기본값은
  `현재 프로젝트 max roundNo + 1`(프로젝트 없으면 1), noteId는 ''.
- 입력한 roundNo가 현재 프로젝트에 이미 있으면 칸 옆에 옅은 힌트 "기존 N차 재분석" 표시.
- `inferRoundNo(name)` (순수) — **board-derive.js에 배치**(A·B 바이트 동일, 두 앱 공용). 우선순위
  1) `(\d+)\s*차` (N차·N회차) → 2) `버전\s*(\d+)` → 3) 첫 정수 → 없으면 null.

프로젝트가 선택돼 있어야 회차가 저장된다(기존과 동일). 프로젝트 미선택 시 회차 번호칸은
비활성/무시하고 기존처럼 저장 없이 보드만 렌더.

## 5. 저장 / 렌더 배선 변경 (`index.html`)

`renderBoard`의 자동 저장 분기:
- `addRound(state, current, {roundNo, noteId, title, raw})` → 반환 id로 `currentRoundId` 설정.
- 저장 직후 이 회차의 **자기 기준**을 계산: `b = findBaseline(project, roundNo)`;
  `setRoundBaseline(current, thisId, b?b.roundNo:null, b?b.ts:'')`.
- diff 기준도 `findBaseline`로 교체: 기존 `rounds[idx-1]` → `findBaseline(project, 현재 roundNo)`.
  기준이 없으면(최소 회차) diff=null(기존 첫 회차와 동일 렌더, 회귀 없음).

## 6. 재분석 연쇄 / 기준 오래됨 (지시 19)

**staleness 판정(파생)**: 회차 Y가 stale ⇔ 저장된 `(Y.baselineNo, Y.baselineStamp)` 가
현재 올바른 기준 `(findBaseline(project,Y.roundNo)?.roundNo, .ts)` 와 다르다.
- 재분석으로 기준 회차의 ts가 바뀌면 stamp 불일치 → stale.
- 중간 회차를 새로 분석하면 후속 회차의 기준 roundNo 자체가 바뀜 → No 불일치 → stale.
- 최소 회차(baseline 없음)는 항상 non-stale.
- **단, `baselineNo === null`(첫 회차 또는 마이그레이션된 레거시 회차 = 미스탬프)은 stale 대상에서 제외.**
  재분석 추적은 "한 번이라도 기준과 함께 분석되어 baselineNo가 찍힌(비-null)" 회차에만 적용한다 →
  기존 저장 데이터(baselineNo 전무)가 로드 즉시 거짓 stale로 뜨는 것을 방지.

**분석 직후 흐름**: roundNo N을 저장하면
1. 영향 집합 = N을 제외한 회차 중 위 판정으로 새로 stale이 되는 것들(실무상 직접 후속 1건).
   raw는 분석 결과라 바뀌지 않으므로 연쇄는 1단계로 끝난다(후속의 후속은 기준 raw 불변).
2. 영향 집합이 비어 있지 않으면 확인창:
   *"연쇄 재계산이 필요합니다 (영향 회차: N차[, M차]) — 지금 다시 계산할까요?"*
   - **수락** → 각 영향 회차에 `setRoundBaseline`으로 현재 올바른 기준(No, ts) 정합화 → stale 해제.
   - **거부** → 그대로 두면 판정상 stale 유지.

**표시**: 히스토리 목록에서 stale 회차 행에 `⚠ 기준 데이터 오래됨` 배지. diff/digest는 라이브라
열람하면 항상 현재 기준 대비 최신 값이 보이며, 배지는 "기준 회차가 재분석된 뒤 아직 정합화되지
않았다"는 신호다(수락 또는 그 회차 재분석으로 해제).

## 7. 히스토리 목록 (지시 20)

`renderProjHistory`는 `roundsSortedByNo(project)`로 **roundNo 오름차순** 렌더.
각 행: `N차` 라벨 + 제목 + 실제 처리 일시(`fmtUpdatedAt(ts)`) 병기 + (stale면) 경고 배지.
처리 순서와 회차 순서가 다를 수 있음을 처리 일시로 시각 구분.

## 8. A·B 바이트 동일 · 테스트

- 바이트 동일 대상: `project-store.js`(변경), `board-diff.js`(무변경), 기타 4개(무변경).
  `inferRoundNo`는 board-derive.js에 넣으면 이 파일도 바이트 동일 대상 → A·B 동시 반영.
- index.html은 A·B 별개 파일이지만, `addRound` 반환 shape 변경 등 호출부는 **양쪽 모두** 갱신해야
  A가 깨지지 않는다.
- 테스트(`테스트/*.test.js`, node:test): 추가
  - roundNo 마이그레이션(누락→1,2,3 / 중복·비정수 보정 / 멱등)
  - addRound upsert(같은 roundNo 교체·id 유지·ts 갱신, 다른 roundNo append)
  - `findBaseline` — **지시 18 예시**(2→5→3→1→4 처리해도 5→3, 3→2, 4→3, 1→없음)
  - staleness/`roundsUsingBaseline`(재분석·중간삽입 케이스)
  - `inferRoundNo` 케이스, `roundsSortedByNo`
  - 기존 바이트 동일 픽스처는 A·B를 동일 편집하므로 계속 통과.

## 9. 마이그레이션

기존 localStorage 데이터(`jjc-projects`)는 `sanitizeProject`가 로드 시 자동 이관(§3, 멱등, 비파괴).
별도 마이그레이션 코드/버전 플래그 없음. 되돌리기 안전(로컬·per-origin).
